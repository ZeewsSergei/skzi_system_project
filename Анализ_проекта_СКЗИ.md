# Анализ проекта «Учёт СКЗИ» v5.0
### Автор анализа: технический аудит кодовой базы

---

## 1. ОБЩАЯ ОЦЕНКА ПРОЕКТА

Проект представляет собой **полноценное desktop-приложение** на PyQt6 + SQLite для учёта средств криптографической защиты информации (СКЗИ) в организации. Архитектура трёхзвенная (Repository → Service → UI), код написан системно и логично. Для solo-разработки уровень выше среднего.

**Итоговая оценка: 6.5 / 10**

---

## 2. СИЛЬНЫЕ СТОРОНЫ

### Архитектура
- Чёткое разделение на слои: `repositories/` → `services/` → `forms/` + `widgets/`. Бизнес-логика не смешана с UI.
- Паттерн **Singleton** для `DatabaseManager` и `AppLogger` — правильное решение для desktop-приложения с одним соединением к БД.
- Система **сигналов** (`AppSignals`) через `pyqtSignal` — грамотный механизм реактивного обновления вкладок без прямых зависимостей между компонентами.
- `BaseRepository` с шаблонными CRUD-методами снижает дублирование кода в справочниках.

### База данных
- Схема хорошо нормализована: справочные таблицы вынесены отдельно (`skzi_names`, `media_types`, `arm_types` и т.д.), FK настроены корректно.
- `_upgrade_schema()` в `DatabaseManager` обеспечивает безболезненную миграцию старых баз — это зрелое решение.
- `PRAGMA foreign_keys = ON` и `PRAGMA journal_mode=WAL` настроены правильно.
- Таблица `audit_log` с полями `old_value`, `new_value`, `changed_fields` — профессиональный подход к аудиту.

### Функциональность
- Полный жизненный цикл СКЗИ: поступление → регистрация → установка → контроль → уничтожение.
- Отдельные модули для ViPNet Client и СЗИ от НСД — правильное решение, т.к. они имеют отличную бизнес-логику.
- Массовое уничтожение с подтверждением через диалог.
- Импорт из Excel и экспорт в Excel + Word.
- Резервное копирование с возможностью восстановления.
- Системный трей с уведомлениями.
- `DateTableWidgetItem` с кастомным `__lt__` для корректной сортировки дат в таблицах — правильно.
- Строка фильтров под каждым столбцом — хорошее UX-решение.
- Обязательная смена пароля при первом входе (`must_change_password`).
- PBKDF2-SHA256 с солью для хранения паролей — профессиональный стандарт.

### Документация
- Вкладка «Справка» содержит полное руководство пользователя прямо в приложении.
- Таблица соответствия полей БД русским названиям — очень полезно.

## 3. КРИТИЧЕСКИЕ ОШИБКИ (нужно исправить немедленно)

### 3.1. SQL-инъекция в `mass_mark_destroyed`
**Файлы:** `skzi_repository.py`, `szi_nsd_repository.py`, `vipnet_repository.py`

```python
# ТЕКУЩИЙ КОД (уязвимость):
placeholders = ','.join(['?' for _ in ids])
query = f"... WHERE id IN ({placeholders})"
params = [withdrawal_date, destruction_act_num, withdrawer_fio] + ids
```
Это **не SQL-инъекция**, но есть риск ошибки при передаче пустого списка `ids`. Если `ids = []`, то `IN ()` — синтаксическая ошибка SQLite. Нужна проверка:
```python
if not ids:
    return
```

### 3.2. Отсутствует проверка прав доступа в UI
**Файл:** `main_window.py`

Роли (`ADMIN`, `OPERATOR`, `AUDITOR`) хранятся в БД, но нигде в интерфейсе **не проверяются**. Кнопки «Зарегистрировать», «Удалить», «Уничтожить» доступны всем пользователям независимо от роли. AUDITOR должен только читать данные, но физически может всё.

```python
# Нужно добавить везде:
if self.user['role'] == 'AUDITOR':
    btn_add.setEnabled(False)
    btn_destroy.setEnabled(False)
```

### 3.3. Небезопасное восстановление БД
**Файл:** `backup.py`

```python
def restore_db(backup_path, password=None):
    db_manager = DatabaseManager()
    db_manager.close()  # закрывает соединение
    with zipfile.ZipFile(backup_path, 'r') as zf:
        zf.extract('skzi_registry.db', ...)
```
После `db_manager.close()` синглтон `DatabaseManager._instance` остаётся в памяти с `_initialized = True`. При следующем вызове `DatabaseManager()` он вернёт уже закрытый объект, не переоткрыв соединение. Необходимо добавить сброс синглтона:
```python
DatabaseManager._instance = None
```

### 3.4. `control_repository.py` использует прямые соединения вместо `DatabaseManager`
```python
def get_connection():
    conn = sqlite3.connect(get_db_path())
    return conn
```
Это **отдельное соединение**, вне транзакций синглтона. При параллельных записях возможны конфликты WAL-журнала. Все операции должны идти через `DatabaseManager`.

### 3.5. `ControlService` не вызывает сигналы и не ведёт аудит
**Файл:** `control_service.py`

```python
class ControlService:
    def register_control(self, skzi_id, date, result, inspector):
        return add_control(skzi_id, date, result, inspector)
```
Нет `app_signals.control_changed.emit()`, нет `AuditService.log()`. Контрольные проверки никак не попадают в аудит — нарушение требований к учёту СКЗИ.

### 3.6. `ControlDialog` передаёт дату в неверном формате
**Файл:** `control_dialog.py`
```python
date = self.date_edit.date().toString("dd-MM-yyyy")  # дефис, не точка!
```
В БД даты хранятся в ISO-формате (`yyyy-MM-dd`). Передаётся `dd-MM-yyyy` — сортировка и фильтрация в таблицах будут некорректными.

## 4. СЕРЬЁЗНЫЕ ПРОБЛЕМЫ

### 4.1. Дублирование класса `DateTableWidgetItem`
Класс определён **в каждом файле отдельно**: `main_window.py`, `training_tab.py`, `szi_nsd_tab.py`, `destruction_tab.py`, `vipnet_tab.py`. Это 5 копий одинакового кода. Нужно вынести в `utils/date_utils.py` и импортировать.

### 4.2. Проблема с форматом дат в `training_service.py`
```python
self.date_edit.setDate(QDate.fromString(training['training_date'], "dd.MM.yyyy"))
```
Но в БД даты хранятся как `yyyy-MM-dd`. При загрузке записи для редактирования дата может не распознаться. В `training_dialog.py` аналогичная проблема в `load_record()`.

### 4.3. `DictionaryService` — огромный код с повторениями
**Файл:** `dictionary_service.py` содержит 8 практически идентичных методов `get_or_create_*`. Каждый — ~15 строк с одинаковым паттерном. Нужна шаблонная функция:
```python
def _get_or_create(self, repo, name, table_name, description, username):
    if not name:
        return None
    existing = repo.get_by_name(name)
    if existing:
        return existing['id']
    new_id = repo.add(name)
    self.audit.log("CREATE", table_name, new_id, username, f"{description}: {name}")
    return new_id
```

### 4.4. Два набора репозиториев для справочников
Существуют **одновременно**:
- `repositories/dictionary_repositories.py` (наследуют `BaseRepository`)
- Отдельные файлы: `skzi_name_repository.py`, `media_type_repository.py`, `arm_type_repository.py` и т.д.

При этом `DictionaryService` импортирует **отдельные файлы**, а `dictionary_repositories.py` — мёртвый код. Нужно убрать дублирование.

### 4.5. `audit_repository.py` — мёртвый код
`AuditRepository` не используется нигде — везде напрямую используется `AuditService`. Файл нужно удалить или использовать.

### 4.6. Метод `filter_registry` не сбрасывает строки, скрытые фильтрами столбцов
**Файл:** `main_window.py`
```python
def filter_registry(self):
    for i in range(self.reg_table.rowCount()):
        if self.reg_table.isRowHidden(i):
            continue  # ОШИБКА: скрытые фильтром строки не проверяются при сбросе поиска
```
При очистке строки быстрого поиска строки, скрытые столбцовыми фильтрами, могут некорректно отображаться. Аналогичная проблема во всех вкладках.

### 4.7. `register_skzi` не проверяет уникальность `skzi_number` и `cert_number`
В схеме БД эти поля имеют `UNIQUE`, но при попытке добавить дубль пользователь получит необработанное исключение SQLite. Нужна человеко-читаемая ошибка.

### 4.8. `SziNsdService.register()` проверяет `arm_id`, которого ещё нет
```python
existing = self.repo.get_by_arm_id(data['arm_id']) if data.get('arm_id') else None
```
В форме `SziNsdForm` поле `arm_id` не передаётся — передаётся `arm_serial`. `arm_id` создаётся позже через `get_or_create_arm`. Проверка бесполезна и никогда не срабатывает. Аналогично в `VipNetService`.

### 4.9. `skzi_service.py` — метод `get_all_active` содержит дублирующий SQL
В классе `SkziService` есть свой SQL-запрос в `get_all_active()`, при этом `SkziRepository` тоже имеет `get_all_active()`. Два разных запроса для одной цели — риск рассинхронизации.

## 5. УЛУЧШЕНИЯ КАЧЕСТВА КОДА

### 5.1. Нет транзакций при составных операциях
`register_skzi` в сервисе делает несколько операций (создание АРМ, создание записи реестра, аудит) без единой транзакции. При сбое на середине данные окажутся в несогласованном состоянии:
```python
# Нужно:
try:
    arm_id = self.arm_service.get_or_create_arm(arm_data)
    self.repo.add_skzi(registry_data)
    self.audit.log(...)
    self.db.commit()
except Exception:
    self.db.rollback()
    raise
```

### 5.2. `print()` вместо логирования
По всему коду разбросаны `print()` для отладки:
```python
print("Диалог СКЗИ завершён, данные обновятся по сигналу")
print(f"DictionaryService.get_or_create_skzi_name: name='{name}'")
```
В production-коде их быть не должно. Использовать только `app_logger`.

### 5.3. Голые `except` без типов исключений
```python
try:
    qdate = QDate.fromString(install_date, "yyyy-MM-dd")
except:
    pass
```
`except:` перехватывает даже `SystemExit` и `KeyboardInterrupt`. Всегда указывайте тип: `except Exception:` или конкретный тип.

### 5.4. `skzi_account` передаётся в `arm_id` при проверке
В `SziNsdService` и `VipNetService` поле `skzi_account` или `arm_serial` в сообщениях об ошибках иногда перепутаны.

### 5.5. Магические строки статусов
По всему коду разбросаны `'ACTIVE'` и `'DESTROYED'` как строковые литералы. При опечатке ошибка найдётся только в runtime. Нужен Enum:
```python
class SkziStatus(str, Enum):
    ACTIVE = 'ACTIVE'
    DESTROYED = 'DESTROYED'
```

### 5.6. Жёстко закодированные значения в `szi_nsd_form.py`
```python
self.szi_nsd.addItems(["Dallas Lock", "Secret Net"])
```
Значения загружаются из справочника чуть позже в `load_dictionaries()`, но предварительно захардкожены. Это создаёт дубли в списке.

## 6. ЧТО УПУЩЕНО В ПРОЕКТЕ

### 6.1. 🔴 Нет уведомлений об истекающих сроках СКЗИ
Поле `expiry_date` хранится в БД, но **нет никакой индикации** записей с истекающим или истёкшим сроком. Критически важная функция для регулятора:
- Подсветка строк в реестре (жёлтый — истекает через 30 дней, красный — истёк).
- Уведомление при запуске приложения.
- Отдельный фильтр «Истекающие».

### 6.2. 🔴 Нет управления пользователями в интерфейсе
Администратор может создать первого пользователя через `FirstRunDialog` и других через `RegisterWindow`, но **управление пользователями (список, удаление, блокировка, сброс пароля)** не реализовано как экран. `RegisterWindow` вообще нигде не вызывается из `main_window.py` — мёртвый код.

### 6.3. 🔴 Нет управления справочниками в интерфейсе
Справочники (`skzi_names`, `media_types`, `arm_types`, `os_versions`, `antiviruses`, `addresses` и т.д.) можно только импортировать из Excel или добавлять по одному через комбобоксы в формах. **Нет экрана просмотра/редактирования/удаления справочников** — это серьёзный пробел для администратора.

### 6.4. 🟡 Нет поля «Учётный номер» (регистрационный номер СКЗИ)
По регламенту ФСБ учёт СКЗИ ведётся в журнале, где каждая запись имеет **порядковый учётный номер**. В реестре такого поля нет — поиск ведётся по заводскому номеру и номеру сертификата.

### 6.5. 🟡 Отсутствует учёт поступления СКЗИ (склад / оприходование)
Сейчас СКЗИ сразу регистрируется как «выданное и установленное». В реальной практике СКЗИ сначала поступают на склад, затем выдаются. Нужен статус `IN_STOCK` и отдельный журнал поступления.

### 6.6. 🟡 Нет связи между `skzi_registry` и `vipnet_installations`
ViPNet Client — это тоже СКЗИ, но хранится в отдельной таблице. В отчёте «Все сведения учёта» они суммируются через `UNION`, но **единого инвентарного номера** нет. При экспорте журналов ЭП данные о ViPNet не включаются.

### 6.7. 🟡 Нет учёта возврата СКЗИ (без уничтожения)
Статус бывает только `ACTIVE` или `DESTROYED`. В реальности СКЗИ может быть **возвращено** (например, при увольнении сотрудника) и **передано другому** без уничтожения. Нужен статус `RETURNED` или `TRANSFERRED`.

### 6.8. 🟡 Нет привязки контрольных проверок к сотруднику
`control_checks` привязан к `skzi_registry_id`, но не существует для ViPNet Client и СЗИ от НСД. Контрольная вкладка (`ControlTab`) не интегрирована с главным сигнальным механизмом и фактически изолирована.

### 6.9. 🟡 Нет экспорта в форматах Word (docx)
В справке написано «Экспорт в форматы Excel и Word (docx)», но в `excel_exporter.py` экспорт только в Excel. Word-экспорта нет. Это обман пользователя.

### 6.10. 🟡 Нет истории изменений записи СКЗИ
Нет возможности посмотреть историю изменений конкретной записи. Аудит есть, но он общий. В требованиях к учёту СКЗИ важно знать: кто, когда и что менял в записи.

### 6.11. 🟢 Нет поиска по реестру с учётом вложенности
Фильтр ищет в строках таблицы, но не в связанных данных. Например, нельзя найти «все СКЗИ сотрудников отдела X» через единый фильтр — нужно использовать расширенный диалог (`FilterDialog`), который существует, но **не подключён к главному окну**.

### 6.12. 🟢 Нет автоматической нумерации актов
При создании акта уничтожения номер вводится вручную. Можно предложить автоинкрементный номер по шаблону.

### 6.13. 🟢 Нет печати / предпросмотра
Экспорт в Excel есть, но нет прямой печати или предпросмотра из приложения.

### 6.14. 🟢 Нет привязки АРМ к конкретному кабинету/адресу через нормализацию
В таблице `arm` поля `cabinet_number` и `install_address_id` есть, но в форме СКЗИ пользователь каждый раз вводит кабинет заново. При изменении кабинета АРМ обновляется, но история перемещений не ведётся.

## 9. СТРУКТУРНЫЕ ПРЕДЛОЖЕНИЯ

### Предлагаемая доработка схемы БД

```sql
-- Добавить статус IN_STOCK и RETURNED
-- Изменить CHECK constraint:
ALTER TABLE skzi_registry ADD COLUMN status TEXT 
    CHECK(status IN ('STOCK','ACTIVE','RETURNED','DESTROYED')) DEFAULT 'STOCK';

-- Добавить учётный номер
ALTER TABLE skzi_registry ADD COLUMN accounting_number TEXT;

-- История перемещений АРМ
CREATE TABLE arm_history (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    arm_id INTEGER NOT NULL,
    change_date DATE NOT NULL,
    old_cabinet TEXT,
    new_cabinet TEXT,
    old_address_id INTEGER,
    new_address_id INTEGER,
    changed_by TEXT,
    FOREIGN KEY (arm_id) REFERENCES arm(id)
);

-- Блокировка пользователей
ALTER TABLE users ADD COLUMN is_blocked INTEGER DEFAULT 0;
ALTER TABLE users ADD COLUMN failed_attempts INTEGER DEFAULT 0;
ALTER TABLE users ADD COLUMN last_login TIMESTAMP;
```
